# 2026-09-07 — 2026-09-07 — Layered Architectureの依存方向とRepository

## 1. Problem

あなたは、既存のECサイトの注文機能を保守している。現在のコードは、HTTPハンドラーからDBアクセスまでを1つの層にまとめて実装している。

以下が現在の構成である。

- `OrderHandler`
  - HTTPリクエストを受け取る
  - リクエストのバリデーションを行う
  - 注文金額を計算する
  - `OrderRepository` を呼び出してDBへ保存する
  - HTTPレスポンスを返す
- `OrderRepository`
  - DBへのINSERT/SELECTを行う
- `Order`
  - 注文データを保持するだけの構造体

## 要件

今後、注文処理に以下の変更が入る予定である。

- HTTP API以外に、バッチからも注文処理を実行したい
- 注文金額の計算ルールが今後増える可能性がある
- DBを将来的に別の実装へ変更する可能性がある
- HTTP固有の処理と注文固有のルールを分離したい

現在の実装をLayered Architectureに整理し直すことになった。

## 3. Review

### Correctness
12/30

主な誤りはRepositoryと依存方向の捉え方。

`OrderRepository`をDomain側に置くという発想自体は一部正しいが、Domain / UseCase側にはRepositoryのinterfaceを置き、DBアクセスの具体実装はInfrastructure側に置くべき。

また、BatchはRepositoryではなく、UseCaseを呼び出す別の入口として扱う。

### Strengths

- Handler / UseCase / Domain / Repository / Infrastructureという主要な構成要素を想起できた
- HTTP処理とビジネスロジックを分離しようとしている
- 金額計算をHandlerから切り離してUseCase側へ寄せた
- DB実装をInfrastructureとして分離する発想を持てている

### Gaps

- Domainの責務が「対象の領域を定義する」だけで曖昧
- RepositoryとBatchを混同している
- 「Handler → UseCase → Domain → Repository → Infrastructure」という依存方向の理解が不十分
- 依存性逆転により、UseCaseがDBの具体実装を知らない構造を説明できていない
- Repository interfaceと具体実装の区別ができていない

### In practice

基本形は以下。

Handler → UseCase → Domain
Batch → UseCase

UseCase → OrderRepository(interface) ← OrderRepositoryImpl → DB

HTTPから呼んでもバッチから呼んでも注文処理をUseCaseに集約し、DBの具体実装はInfrastructureに閉じ込めることで、DB変更の影響を上位層へ波及させにくくする。

### Model answer

Handler / Presentation:
HTTPリクエストの受付、HTTP固有のバリデーション、DTO変換、UseCase呼び出し、HTTPレスポンスへの変換。

UseCase / Application:
注文作成などの処理フローを定義し、Domainモデルを利用して処理する。Repository interfaceを利用して保存する。HTTPやDBの具体実装は知らない。

Domain:
Orderなどのドメインモデルや注文そのものに属するビジネスルールを持つ。必要に応じてRepository interfaceなどの抽象を定義する。

Infrastructure:
Repository interfaceの具体実装やDBへのINSERT/SELECTなど、DB製品固有の処理を担当する。

Batch:
RepositoryではなくUseCaseを呼び出す別の入口として実装する。

依存関係の重要なポイントは、UseCaseがDBの具体実装に依存しないこと。

OrderRepositoryは、

UseCase → OrderRepository(interface) ← OrderRepositoryImpl → DB

という形にする。
