# 2026-09-03 — 会議室予約のダブルブッキングを構造で防ぐ

## 1. Problem

### 前提

社内向けの会議室予約システムを新規に作る。会議室は20室。利用者は約300名。予約は30分単位で、営業時間は09:00–21:00。

### 要件

1. 同じ会議室の同じ時間帯を2人が同時に予約できてはならない
2. 予約はキャンセルできる。キャンセル済みの枠は再予約できる
3. 「誰がいつキャンセルしたか」を後から確認できる
4. 会議室ごとの月次利用率を集計する画面がある

### 提出物

- ER図（テキストで可）
- 主要テーブルのDDL
- 要件1をどう構造的に防ぐかの説明
- 要件4のクエリと、必要なインデックス

### 制約

- RDBMSはPostgreSQL 16
- アプリ側の排他制御には依存しない設計にすること
- 30分で書けるところまで

## 2. My answer

reservations テーブルを作る。

```sql
CREATE TABLE reservations (
  id BIGSERIAL PRIMARY KEY,
  room_id BIGINT NOT NULL REFERENCES rooms(id),
  user_id BIGINT NOT NULL REFERENCES users(id),
  start_at TIMESTAMPTZ NOT NULL,
  end_at TIMESTAMPTZ NOT NULL,
  is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (room_id, start_at)
);
```

ダブルブッキングは UNIQUE (room_id, start_at) で防ぐ。キャンセルは is_deleted を true にする。

月次利用率は

```sql
SELECT room_id, count(*) FROM reservations
WHERE start_at >= '2026-09-01' AND start_at < '2026-10-01' AND is_deleted = false
GROUP BY room_id;
```

インデックスは start_at に張る。

キャンセルした人と時刻は… canceled_by と canceled_at を足せばいいと思うが、複数回キャンセルと再予約を繰り返した履歴までは取れない。ここは分からない。

## 3. Review

### 3.1 Correctness

- `UNIQUE (room_id, start_at)` は**要件2と矛盾する**。`is_deleted = true` の行が残っている限り、同じ枠の再予約がユニーク制約違反で弾かれる。論理削除とUNIQUE制約の典型的な衝突。
- 30分単位という前提に対し `start_at`/`end_at` を自由な時刻で持てる構造になっている。1件で複数枠（09:00–11:00）を予約した場合、`start_at` の一意性だけでは重なりを検知できない。09:00–11:00 と 09:30–10:00 が同時に成立してしまう。
- 集計クエリの `count(*)` は「予約件数」であり「利用率」ではない。分母（営業時間の枠数）がないため要件4を満たしていない。

### 3.2 Strengths

- アプリ側の排他に頼らず、DB制約で防ぐという方針の立て方は正しい。制約は要件に合っていないが、アプローチの選択は妥当。
- 外部キーとNOT NULLを最初から入れている。整合性を構造で担保する意識がある。
- 分からない箇所（キャンセル履歴）を隠さず明示した。ここは評価する。実務のレビューでも同じ振る舞いが望ましい。

### 3.3 Gaps

1. **論理削除とUNIQUEの衝突**への対処がない。部分インデックスが最短の解。
   ```sql
   CREATE UNIQUE INDEX uq_active_slot ON reservations (room_id, start_at)
     WHERE status = 'active';
   ```
2. **重なり判定**が枠固定モデルでしか成立していない。30分固定なら「予約1件 = 1枠」に正規化して`reservation_slots`を分けるのが素直。可変長を許すなら排他制約を使う。
   ```sql
   CREATE EXTENSION btree_gist;
   ALTER TABLE reservations ADD CONSTRAINT no_overlap
     EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at) WITH &&)
     WHERE (status = 'active');
   ```
3. **キャンセル履歴**が状態カラムだけでは表現できない。`status` + `reservation_events`（予約・キャンセルの追記専用テーブル）に分けると要件3を満たせる。
4. **is_deleted のBOOLEAN**は状態が3つ以上になった時点で破綻する。`status TEXT CHECK (status IN ('active','canceled'))` のほうが拡張できる。
5. **インデックス**が `start_at` 単独になっている。実際のクエリは `room_id` で絞り `start_at` の範囲を見るので、`(room_id, start_at)` の複合が効く。列順は「等価条件の列を先、範囲条件の列を後」。

### 3.4 In practice

現場ではまず「予約単位は固定か可変か」を要件確認で潰します。30分固定なら`reservation_slots`分割が圧倒的に運用が楽で、排他制約も拡張も要らず、集計も枠数を数えるだけで利用率が出ます。可変長要件が本当にあるときだけ`EXCLUDE`を持ち出す。

`EXCLUDE USING gist`は正しいが、レビューでは「この制約を理解・運用できるチームか」も判断材料になります。読めない制約は事故を呼ぶので、複雑な制約を入れるときはコメントとテストを必ず添えます。

利用率の分母は要件を詰める対象です。「営業時間の全枠」か「稼働日のみ」かで数字が変わり、経営が見る指標なので勝手に決めない。

### 3.5 Model answer

30分固定を前提に、予約と枠を分離する。

```sql
CREATE TABLE reservations (
  id          BIGSERIAL PRIMARY KEY,
  room_id     BIGINT NOT NULL REFERENCES rooms(id),
  user_id     BIGINT NOT NULL REFERENCES users(id),
  status      TEXT NOT NULL DEFAULT 'active'
              CHECK (status IN ('active','canceled')),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE reservation_slots (
  reservation_id BIGINT NOT NULL REFERENCES reservations(id) ON DELETE CASCADE,
  room_id        BIGINT NOT NULL REFERENCES rooms(id),
  slot_start     TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (reservation_id, slot_start)
);

-- 要件1: activeな予約に限り、同一室・同一枠は1件だけ
CREATE UNIQUE INDEX uq_active_slot
  ON reservation_slots (room_id, slot_start)
  WHERE reservation_id IN (SELECT id FROM reservations WHERE status = 'active');
-- ↑ 部分インデックスに副問合せは書けないため、実際は
--   reservation_slots に status を非正規化して持たせるか、
--   キャンセル時に slots を削除する運用にする（後者が単純）

CREATE TABLE reservation_events (
  id             BIGSERIAL PRIMARY KEY,
  reservation_id BIGINT NOT NULL REFERENCES reservations(id),
  event_type     TEXT NOT NULL CHECK (event_type IN ('created','canceled')),
  actor_user_id  BIGINT NOT NULL REFERENCES users(id),
  occurred_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

キャンセル時に`reservation_slots`の行を削除し、`reservation_events`に追記する。これで要件1〜3が同時に満たされる。「消したら履歴が消える」問題はイベント表が引き受けるため、slotsは現在の予約状態だけを表す純粋な構造になる。

利用率:

```sql
SELECT r.id AS room_id,
       count(s.slot_start)::numeric
         / (24 * 26) AS utilization  -- 12時間 × 2枠 × 稼働日数（要件確認事項）
FROM rooms r
LEFT JOIN reservation_slots s
  ON s.room_id = r.id
 AND s.slot_start >= '2026-09-01' AND s.slot_start < '2026-10-01'
GROUP BY r.id;
```

インデックス: `reservation_slots (room_id, slot_start)` はPKと`uq_active_slot`で足りる。

## 6. What I learned

1. 論理削除を入れた時点で、素のUNIQUE制約は使えなくなる。部分インデックスか、状態遷移で行を消す設計に切り替える。
2. 複合インデックスの列順は「等価条件の列を先、範囲条件の列を後」。`WHERE room_id = ? AND start_at BETWEEN ? AND ?`なら`(room_id, start_at)`。
3. 「予約」と「枠」を分けると、重なり判定・集計・キャンセルが同時に単純になる。単位が固定なら分割を先に検討する。
