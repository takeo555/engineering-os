# 2026-09-09 — 論理削除と一意制約が衝突する貸出管理設計

## 1. Problem

社内で利用する「社内備品貸出管理システム」のテーブル設計レビューを担当しています。

現在の利用規模は以下のとおりです。

- 利用者数：8,000人
- 備品数：12,000件
- 1日あたりの貸出申請：3,000件
- データ保持期間：7年
- DB：PostgreSQL
- アプリケーションはWeb APIから利用する
- 備品の廃棄や利用者の退職により、データを画面上から非表示にする必要がある
- 退職者や廃棄済み備品の過去の貸出履歴は保持する必要がある

## 要件

次の設計で運用を開始することになりました。

CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    employee_code VARCHAR(20) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL,
    deleted BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

CREATE TABLE items (
    id BIGSERIAL PRIMARY KEY,
    management_code VARCHAR(30) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    deleted BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

CREATE TABLE loans (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    item_id BIGINT NOT NULL REFERENCES items(id),
    loaned_at TIMESTAMP NOT NULL,
    returned_at TIMESTAMP NULL,
    created_at TIMESTAMP NOT NULL
);

アプリケーションでは、以下のルールで処理します。

- users.deleted = false の利用者だけを通常画面に表示する
- items.deleted = false の備品だけを通常画面に表示する
- 利用者の新規登録時、employee_code が既存データに存在しないことをアプリケーションで確認する
- 備品の新規登録時、management_code が既存データに存在しないことをアプリケーションで確認する
- 退職者や廃棄済み備品は、deleted = true に更新する
- 貸出履歴は削除しない
- 1つの備品を同時に複数人へ貸し出してはいけない
- 貸出中かどうかは returned_at IS NULL で判定する

## 2. My answer

貸出履歴は一定時間経過後に削除しないと重くなってしまう。
退職者や廃棄済み備品は、`deleted = true` に更新するのではなく、そのデータ自体を削除としないと、そのidは使えなくなってしまう

## 3. Review

論理削除と一意制約の衝突を指摘できず、ID再利用のために物理削除するという逆方向の判断になった。貸出履歴の保持期間7年と「一定時間後に削除する」という考えも整合していない。

## 6. What I learned

- IDは再利用する必要がなく、履歴を参照するデータは安易に物理削除しない。
- 論理削除を採用したら、UNIQUE制約が削除済みデータまで対象にしていないか確認する。
- データ量が増える問題は、保持要件を破って削除するのではなく、パーティショニングやアーカイブなどで解決する。
