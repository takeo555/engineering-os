# 2026-09-11 — 備品一覧APIのページングと責務分離

## 1. Problem

### 前提

社内向けの備品貸出画面を、Go APIとNext.jsで実装しています。

- Go API：`GET /api/items`
- Next.js：App Router
- 利用者数：5,000人
- 備品数：20,000件
- 1画面あたりの表示件数：20件
- APIの平均応答時間目標：300ms以内
- 備品一覧はログイン済みユーザーだけが利用できる
- 備品には `name`、`category`、`status` がある
- 一覧には「備品名」「カテゴリ」「貸出可能か」を表示する
- 今後、検索条件とページングを追加する予定

### 現在の実装

Go API:

    type Item struct {
        ID       int64  `json:"id"`
        Name     string `json:"name"`
        Category string `json:"category"`
        Status   string `json:"status"`
    }

    func GetItems(w http.ResponseWriter, r *http.Request) {
        items, err := db.Query(`
            SELECT id, name, category, status
            FROM items
            ORDER BY id DESC
        `)
        if err != nil {
            http.Error(w, "internal error", http.StatusInternalServerError)
            return
        }
        defer items.Close()

        var result []Item
        for items.Next() {
            var item Item
            if err := items.Scan(
                &item.ID,
                &item.Name,
                &item.Category,
                &item.Status,
            ); err != nil {
                http.Error(w, "internal error", http.StatusInternalServerError)
                return
            }
            result = append(result, item)
        }

        json.NewEncoder(w).Encode(result)
    }

    }

## 2. My answer

DBにある20000件を全て取得してし表示してしまう、２０件で区切る仕様が反映されていない。goで２０件ごとにDBからgetし、それをjsonにしてページ１と名付ける。それをnextがページごとにfor文で取得するようにコードを修正する。 ページnを取得する場合は、20*(n-1)+1から取得するようgoで記述。ただし、１度に何ページ表示して良いかは要件詰めが必要。
認証が全く実装されていない。nextで画面を見せて良いかの認証、goでリクエストを許可して良いのかの認証の記述を追加する。 
goのコードが関数が一つで重い。handler層でHTTPリクエストを受けるレスポンスする、usecaseで20件までをページ１として取得するというようなビジネスロジックを記述、repository層にDB情報を記述する。すると、getitemsが重くなることを防げ、微修正の時も周りにあまり影響を与えない

## 3. Review

### 3.1 Correctness

22/30

主な指摘は正しい。

- 20,000件を全件取得している点を問題として認識できている
- DB側で20件に絞って取得する方向を示せている
- ページングの基本的な計算 `20 * (n - 1)` を理解できている
- 認証について、Next.jsでの画面制御とGo API側でのリクエスト許可を分けて考えられている
- Handler / Usecase / Repositoryへの責務分離を指摘できている

一方、「Goで20件ごとにDBからgetして、それをJSONにしてページごとにNext.jsがfor文で取得する」という表現は不適切。必要なページだけをAPI経由で取得する設計とするべき。

また、ページnの取得は `20 * (n - 1)` をOFFSETとして考えるのが正確。

### 3.2 Strengths

- 大量データを全件取得することによる問題に気づけた
- DB側でページングする方向へ修正できた
- Next.jsとGo APIの認証・認可の責務を分けて考えられた
- Handler / Usecase / Repositoryという責務単位を意識できている
- 今後の検索・ページングを見越して設計を考えられている

### 3.3 Gaps

- ページングについて、`LIMIT 20 OFFSET 20 * (page - 1)` の具体化が不足
- OFFSET方式では大量データやデータ追加・削除時に問題が起こり得る点を説明できていない
- Usecaseの責務を「20件まで取得」と固定しており、ユースケースとしての責務定義がやや狭い
- レイヤー分離の目的を「関数が重くなるのを防ぐ」「微修正の影響を減らす」と捉えており、「責務と変更理由を分離する」という本質まで説明できていない
- DB・API・画面それぞれで何を保証するかの整理が不足
- 不足している前提として、ページング中のデータ追加・削除時の整合性や、ページング方式を決める条件を明確に指摘できていない

### 3.4 In practice

基本的には以下の流れにする。

    Next.js
      ↓ page=1
    Handler
      ↓
    Usecase
      ↓
    Repository(interface)
      ↓
    Repository実装
      ↓
    DB

DBでは必要な20件だけ取得する。

例えばOFFSET方式なら、

    LIMIT 20 OFFSET 20 * (page - 1)

とする。

認証については、Next.js側で未ログインユーザーを画面から適切に制御しつつ、Go API側でも認証・認可を行う。Next.jsで画面を隠すことだけをセキュリティ境界にしない。

レイヤー分離では、単に関数を軽くするのではなく、「HTTPの変更」「業務ルールの変更」「DB実装の変更」という異なる変更理由を分離することが重要。

また、20,000件程度ならOFFSET方式は現実的な選択肢だが、データ量が大きくなった場合や一覧取得中のデータ変動を強く意識する場合は、IDなどを利用したカーソルページングも候補になる。

### 3.5 Model answer

最も重要な問題は、20,000件をDBから全件取得してNext.jsへ渡している点。画面には20件しか必要ないため、DB側で `LIMIT` を使って必要な件数だけ取得するべき。

ページングをOFFSET方式で実装するなら、例えば1ページ20件として、

    page=1 → LIMIT 20 OFFSET 0
    page=2 → LIMIT 20 OFFSET 20
    page=3 → LIMIT 20 OFFSET 40

とする。

Next.jsは必要なページをAPIへ要求し、Go APIはHTTPパラメータの受付・バリデーション・レスポンスを担当する。

Go内部は、

    Handler → Usecase → Repository(interface) ← Repository実装 → DB

のように責務を分ける。

HandlerはHTTP固有の処理、Usecaseは「備品一覧を取得する」というアプリケーション上の処理、RepositoryはDBからデータを取得する責務を持つ。

認証については、Next.js側で画面表示を制御するだけでは不十分。Go API側でも認証・認可を行い、直接APIを呼ばれた場合にも不正な利用を防ぐ必要がある。

また、ページングでは「データが取得途中に追加・削除された場合に重複や取りこぼしを許容するか」という前提が不足している。要件によってはOFFSETではなくカーソルページングを検討する。
