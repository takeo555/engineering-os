# Track: Web / API / HTTP

## Outcome

要件からAPIのエンドポイント・入出力・エラー・認可・冪等性を設計し、クライアントが安全に再送できる契約を書ける。

## Topic map

| Area | L1 | L2（現在） | L3 |
|---|---|---|---|
| HTTP基礎 | メソッドとステータス | 適切なステータスの選択と設計 | キャッシュヘッダの設計 |
| リソース設計 | URL設計の基本 | 要件からリソースと関係を定義する | RESTとRPCの使い分け |
| エラー設計 | 4xx / 5xxの区別 | 機械可読なエラー形式を定義する | 部分失敗とリトライ指示 |
| 冪等性 | GET/PUTの性質 | 冪等キーで二重実行を防ぐ | Exactly-once風の設計と限界 |
| 認証認可 | 認証と認可の違い | トークン検証と権限チェックの置き場所 | 委譲・スコープ設計 |
| バージョニング | URLバージョン | 後方互換な変更の判断 | 段階的移行と廃止計画 |
| 性能 | N+1の存在 | ページング・フィルタの設計 | キャッシュ層と無効化戦略 |

## Recurring question forms
 
- 与えられた業務要件のAPIを設計する（エンドポイント・入出力・エラー）
- 決済や予約などの操作を冪等にする設計を書く
- 与えられたAPI仕様の問題点を3つ指摘する
- 破壊的変更を避けて機能追加する方法を設計する
- 一覧APIが遅い原因を構造から説明する

## Retest triggers

- 冪等キーの保存期間と衝突時の挙動を定義できなかった
- 401と403の使い分けを説明できなかった
- リトライ安全なエラー設計ができなかった
