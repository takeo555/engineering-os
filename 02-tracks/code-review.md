# Track: Code Review

## Role in Engineering OS

**Design専用Track（15分・5軸採点）。Drill 出題対象ではない。**

Design 15分問題の4Track の1つ。weight は 25%。**新設Track**。

コードレビューは「言語知識＋設計知識＋実務経験」を統合する独立スキル。他Trackのレビュー日として消化するのではなく、専用Trackとして鍛える。

## Outcome

与えられたコードや設計を読み、影響の大きい順に3〜5点の指摘を書き、直し方を示せる。「何となく違和感がある」で止めず、原則に紐付けて言語化できる。

## Topic map

| Area | L1 | L2（現在） | L3 |
|---|---|---|---|
| 指摘の優先順位付け | Bug と Style を区別する | Bug / Design / Style を優先度で並べる | 影響半径とコストで並べる |
| 責務の混在 | 1関数が長すぎることに気づく | Handler にビジネスロジックがある等の混在を指摘 | Domain と Application の境界侵犯を指摘 |
| 命名 | 分かりにくい変数名を指摘 | 命名が概念と一致していない箇所を指摘 | ドメイン用語と技術用語の混在を指摘 |
| エラー処理 | エラーを握りつぶしている箇所を指摘 | 呼び出し側で分岐できない形を指摘 | リトライ安全性を指摘 |
| テスト可能性 | テストがない箇所を指摘 | テスト困難な構造（副作用・時刻依存）を指摘 | 境界にモックを置ける形か指摘 |
| セキュリティ | ハードコードされた秘密を指摘 | SQLインジェクション・XSSの余地を指摘 | 認可の抜けを指摘 |
| パフォーマンス | 明らかなN+1を指摘 | クエリ・キャッシュの構造問題を指摘 | 到達し得ないSLOへの実装を指摘 |
| レビューの伝え方 | 一方的な指摘にしない | 選択肢と代償を示して質問形式にする | 相手のコンテキストを含めて議論を設計する |

## Recurring question forms

- 与えられたGoコード / Next.jsコード / Pythonコード の指摘点を影響順に3つ
- 与えられたPRの説明文とdiffから、レビュアーが最初に確認すべき箇所を書く
- 悪いレビューコメントを与え、書き直す（伝わり方を含めて）
- 自分のコードを他人視点でレビューする
- 「LGTMだが後で問題になる」箇所を指摘する

## Retest triggers

- Bug と Design のどちらが優先か判断できなかった
- 責務混在に気づかず、命名だけ指摘してしまった
- エラー処理の抜けを見逃した
- レビューコメントが命令口調で、代案を示していなかった

## Design側の題材として

Code Review Track では、Coding Language カテゴリで扱っている Go / Next.js / Python / Terraform のコードを題材として使う。Terraform については、HCLコードのレビュー（module境界、hardcoded value等）を含める。
