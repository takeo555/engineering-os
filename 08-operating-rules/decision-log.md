# Decision Log

構造・目的・運用ルールを変えた理由を残します。日々の学習内容は書きません。

## Template

```markdown
## YYYY-MM-DD — <決定>

- **背景:** 何が問題だったか
- **決定:** 何をどう変えたか
- **代替案:** 検討して採らなかったもの
- **代償:** 何を失うか
- **見直し条件:** どうなったら再検討するか
```

## 2026-09-18 — 自前MCPコネクタへ切り替え、TODAY.md を新設、cron を前倒しする

- **背景:** 2026-09-11 を最後に記録が7日間ゼロ。調べると GitHub 側は無傷で、`build-context` は毎日成功していた。折れていたのは Claude 側の入口と出口で、原因は3つあった。
  1. **朝の CONTEXT.md が毎日「前日分」だった。** `context.yml` の cron は `0 21 * * *`（06:00 JST）だが、GitHub のスケジュール遅延で実際の起動は 22:49〜23:40 UTC（**07:49〜08:40 JST**）。07:00 の定期タスクより1〜2時間遅い。毎時 `:00` は最も混む枠で、そこを指定していた
  2. **`review-facts` が一度も実行されていなかった**（全ワークフロー実行25件中0件）。こちらも日曜 `0 12 * * 0` という `:00` 枠。`WEEKLY_CONTEXT.md` の「生成: 2026-09-14」は手元実行の結果で、週次レビューも死んでいた
  3. **モバイルで割り当てを取得できない。** Project の指示欄に書かれただけのURLは取りに行かず、Knowledge検索に落ちて「CONTEXT.md がプロジェクトにありません」と答える。2026-09-16 に jsDelivr ミラー追加と「必ずURLを開け」の明記で対処したが、どちらも同じ壁に当たって効かなかった。そのうえ取得失敗時が**ハードストップ**（0問で終了）だったため、失敗した朝はそのまま欠損になっていた
- **決定:**
  - **`TODAY.md` を新設。** `CONTEXT.md` 6.7KB のうち毎日変わるのは約30行だけで、残りは Level/Format の定義・弱点一覧・履歴という静的な情報だった。試験官が読むのは `TODAY.md`、`CONTEXT.md` は人が経緯を追うための全量版にする
  - **cron を前倒しし `:00` を避ける。** 日次は `10 18`（03:10 JST）＋予備 `40 20`（05:40 JST）、週次は `35 08 * * 0`（17:35 JST）、月次は `35 09 1 * *`。遅延3時間を吸収しても 07:00 / 21:00 に間に合う
  - **取得を4段の梯子にする。** `eos_today` ツール → raw URL → jsDelivr → 貼付依頼 → **おまかせ出題**。おまかせは曜日から Track を決め、Format=Explain / Level=L1 に固定する。**0問で終わる日を作らないことを、割り当ての正確さより優先する**
  - **自前MCPサーバ（[`10-automation/mcp/`](../10-automation/mcp/)）へ切り替える。** Cloudflare Workers にツール3つだけ（`eos_today` / `eos_weekly_context` / `eos_post_record`）。投函は再び自動にする
  - **定期タスクを Project の中で作り直し、タスク1で Drill 8問まで出す。** Project 外のタスクは Knowledge が読めず採点できないうえ、結果の会話が Project の外に出て iPhone から辿り着けない（「通知は来るが会話が開けない」の正体）
- **代替案:**
  - **iOS ショートカット**（raw取得→クリップボード→Claude起動、投函もAPI直叩き）。確実だが本人が使わない方針
  - **GitHub 公式リモートMCP**（`api.githubcopilot.com/mcp/`）。2026-09-18 に再確認したが、`github/github-mcp-server` の `install-claude.md` が「requires OAuth authentication through a registered GitHub App (or OAuth App), which is not currently supported」と明記したまま。**すでに一度失敗している経路に朝の運用を賭けない**。10分で試せるので任意テストとしてだけ残す
  - **指示文をさらに強く書く。** 同じ対処を2回試して2回とも効かなかったので採らない
- **代償:** Cloudflare アカウントと Worker の保守が増える。PAT の有効期限切れという新しい故障点ができる（権限は1リポジトリの Issues 読み書き＋Contents 読み取りのみ）。Design 問題は定期タスクでは出ず、Drill に答えてから会話の続きで出る。
- **見直し条件:** この構成で2週間回して記録が週4日未満なら、Drill だけの日を許容する構成（Design を週3日に減らす）を検討する。Worker が月1回以上落ちるなら経路を見直す。

## 2026-09-02 — GitHub書き込みはActionsブリッジで行う

- **背景:** ChatGPTのGitHubコネクタは読み取り専用で、コミット・プッシュができない。dev-modeのカスタムMCPコネクタは書き込み可能だがBusiness/Enterpriseプラン・Web限定で、モバイルから使えない。ChatGPTの定期タスクはGPTsを使えない。

- **代償:** ChatGPT側に定期タスクとカスタムGPTの2つを設定する必要がある。GPT ActionsのためにGitHub PATを1つ発行する。
- **見直し条件:** ChatGPTの標準GitHubコネクタが書き込みに対応した場合、または定期タスクがカスタムGPT/MCPを使えるようになった場合。

## 2026-09-06 — 会社のChatGPT Business Freeワークスペースで運用する

- **背景:** カスタムGPTは個人アカウント（Free / Go / Plus / Pro）では作成できず、Business / Enterprise / Eduのワークスペースが必須であることが判明した。試験官GPTのActionsが唯一のGitHub書き込み経路なので、個人アカウントをいくら課金しても本構成は成立しない。会社には ChatGPT Business Free（¥0・早期アクセス枠）のワークスペースがあり、機能一覧にカスタムGPTが含まれている。また、本取り組みは会社から託されたタスクであり、記録が会社の管理下に入ることは要件と整合する。
- **決定:**
  - 会社のBusiness Freeワークスペースで試験官GPTを作る
  - スマホのChatGPTアプリは会社アカウントでサインインする。個人アカウントは削除せず残す（個人メールはドメイン制限でワークスペースへ招待できず、データ移行の選択肢自体が存在しないため）

  - **GitHubコネクタに依存しない設計にする。** コネクタは読み取り専用な上、Business Freeでの可否が公開されていない。試験官GPTのActionsが直接Issueを読むため、コネクタが無くても全機能が動く
  - **朝の通知の既定をGitHub Mobileにする。** ChatGPT側の機能（定期タスク・コネクタ）の可否に依存せず確実に動き、通知に問題全文が載る。定期タスクが使えるなら併用してよい

- **代償:** スマホのChatGPTが会社アカウントになり、個人利用も会社ワークスペースの記録として残る。個人の履歴は移行できず、見るにはログアウトが必要。Business Freeは公式に案内のない枠のため、終了・有料化のリスクがある。
- **見直し条件:** Business Freeが終了または有料化した場合。その時点で(1)有料Business 2席へ移行、(2)手動フォールバック、(3)採点をActions側へ移設、の3択から選ぶ。**記録はすべてGitHubにあるため、いずれの場合も学習資産は失われない。**

## 2026-09-06 — 個人の無料プランへ切り替え、書き込みをIssue貼付に一本化する

- **背景:** 前項でBusiness Freeワークスペースを前提にしたが、運用を個人アカウントの無料プランで行う方針に変わった。無料プランでは**カスタムGPTを作れず、GPT Actionsも使えない**ため、ChatGPTからGitHubへ書き込む経路が存在しない（コネクタは読み取り専用）。一方で調べたところ、**Projectsは無料でも使え（指示欄＋ファイル5個）、定期タスクも無料で使える**（3個まで・1日1回・時刻は枠指定・Projectのファイルは読めない・GitHubイベントトリガーは有料のみ）ことが分かった。
- **決定:**
  - **試験官はカスタムGPTではなくProjectで常設する。** Knowledgeに `anchors.md` / `examiner-manual.md` / `record-block.md` を置く
  - **書き込みは「記録ブロックをIssueに貼る」の一手に一本化する。** `issues: opened/edited` で `record.yml` が発火し、パースしてコミットする。PATもOpenAI APIキーも不要になった
  - **出題の割り当て（Track / Format / Level / 狙う弱点）はActionsが決め、問題文だけをChatGPTが書く。** ChatGPTに選ばせると弱点の再テストが放置されるため。決定は `CONTEXT.md` に書き、ChatGPTが毎朝読む唯一の入り口とする
  - **Repositoryをpublicにする。** コネクタの可否に依存せず raw URL で読めるようにするため
  - 週次・月次はActionsが数字だけを `WEEKLY_CONTEXT.md` / `MONTHLY_CONTEXT.md` に出し、講評はChatGPTが書いて同じくIssueで保存する
  - 実施ペースを平日5日から毎日へ変更する
- **代替案:** Plusに課金してカスタムGPT + Actionsを使う（コピペは消えるが月額が発生）。出題もActions + OpenAI APIで生成する（月数百円と、APIキー管理が増える）。定期タスクの中で採点まで行う（`anchors.md` を読めず点数がドリフトするため却下）。
- **代償:** 1日1回15秒のコピペが残る。無料枠の上限に当たると軽いモデルに落ちるため採点のブレが有料より大きい。添削の往復を1回に抑える必要がある。Repositoryが公開されるので、会社・顧客の情報は一切書けない。
- **見直し条件:** Plusへ課金した場合（カスタムGPTのActionsで書き込みを自動化すればコピペが消える。Repository側の変更は不要）。または、記録ブロックの貼り忘れが週2回以上になった場合。

## 2026-09-08 — CONTEXT→出題→採点→記録の状態を SESSION で凍結する
